## 핵심 결론

- **Fill/execution reporting: does the order detail expose per-execution records (executionId, time, price, qty) or only aggregate filledQuantity/averageFilledPrice/commission/tax/settlementDate as ADR-0006 observed? Is there a separate executions/transactions endpoint?** — Aggregate only: OrderExecution {filledQuantity, averageFilledPrice, filledAmount, commission, tax, filledAt, settlementDate}, decimal strings, no executionId [toss-openapi-json-1-2-14]. No executions endpoint; GET /api/v1/trades is market ticks [beoks-api-reference-index]. Adapters derive one trade per order [kr-broker-toss-doc]. WebSocket PARTIAL_FILL/FILL events also lack execution id and filledAt [toss-asyncapi-realtime]. Confirms ADR-0006's premise.
- **Is there any WebSocket/SSE/streaming channel (quotes, order events, fills) now or on a roadmap? If REST-only, what is the recommended polling cadence and are there caching/ETag/If-Modified-Since semantics?** — WebSocket exists: wss://openapi-ws.tossinvest.com/ws/v1 (AsyncAPI 1.2.2), channels trade:kr/us, orderbook:kr/us, personal:order [toss-asyncapi-realtime][toss-official-overview-mirror]. Price channels lossy (no sequence/snapshot); personal:order lossless only within a session, not replayed after disconnect, receiver blocked >2 s dropped, resync via REST. Limits: 2 connections/account, 100 subscriptions/connection, 5 declarations/s, 180 s idle timeout, ping every 60 s [toss-asyncapi-realtime][pubdev-toss-invest-api]. SDKs saying 'no WebSocket' describe their own scope [kr-broker-toss-doc][tossinvest-core-pypi]. No documented ETag/If-Modified-Since. Derive polling cadence from group budgets: MARKET_DATA 15/s with up to 200 symbols per price call; order-status polling under ORDER_HISTORY 5/s [toss-official-overview-mirror][toss-openapi-json-1-2-14][tossinvest-core-pypi].
- **Order-type coverage: supported orderType values beyond LIMIT/MARKET (e.g. conditional orders mentioned in press, IOC/FOK, stop/trailing), timeInForce, price/quantity precision and tick validation, orderAmount (USD) semantics for US, and extended-hours flags.** — orderType LIMIT|MARKET; timeInForce DAY (default), CLS (US LIMIT, limit-on-close), OPG (KR opening auction); no IOC/FOK/stop/trailing [toss-openapi-json-1-2-14]. Conditional orders are a separate API: SINGLE/OCO/OTO, expireDate required, one OCO/OTO group per symbol [beoks-current-api-notes][toss-open-api-landing]. No extended-hours flag; calendar sessions and order-hours-closed govern acceptance.

## 질문별 답변

### T1.Q1 · What are the official per-endpoint rate limits (requests/sec, burst, per-client vs per-IP vs per-account), the exact 429 response schema, and whether Retry-After or quota headers are returned? Do limits differ at market open (09:00-09:10) as the blog claims?

🟡 부분 · 우선순위 must · 확신 medium

Token buckets per client x API group (TPS): ORDER 10, ORDER_INFO 6 (3 during 09:00-09:10 KST), ORDER_HISTORY 5, ACCOUNT 1, ASSET 5, AUTH 5, MARKET_DATA 15, MARKET_DATA_CHART 20, MARKET_INFO 3, STOCK 5, STOCK_ALL 1, STOCK_TRADING_TREND 10, RANKING 5, MARKET_INDICATOR(_PRICE) 10, MARKET_INDICATOR_CHART 5, CONDITIONAL_ORDER 5, CONDITIONAL_ORDER_HISTORY 10 [toss-official-overview-mirror]; v1.2.28 adds SECTOR and SECTOR_RANKING at 5/s, and ORDER_INFO remains the only group cut at open [kr-broker-issue-99]. GET /orders and GET /orders/{orderId} belong to ORDER_HISTORY (5/s); POST /orders and /cancel to ORDER [toss-openapi-json-1-2-14]. So the open-window cut hits ORDER_INFO pre-checks (buying-power, sellable-quantity, commissions), not submission or status polling; the blog's 'orders 6/s, 3/s at open' is wrong [brunch-toss-ai-trading]. Headers X-RateLimit-Limit (burst), X-RateLimit-Remaining, X-RateLimit-Reset (seconds to refill one token), X-Request-Id on 200 and 429; Retry-After on 429 only; 429 body {error:{requestId, code: rate-limit-exceeded|edge-rate-limit-exceeded, message, data}} [toss-official-overview-mirror]. Limits can change without notice and the ToS permits lowering during surges [toss-open-api-terms]. Undocumented: a per-IP dimension (edge-rate-limit-exceeded implies a separate edge layer) and the 429 data payload.

### T1.Q2 · Token lifecycle edge cases: does re-issuing within the 24h window really invalidate the prior token immediately; is there a grace period; what does the 401 body look like for expired vs invalidated vs revoked; is there a token-introspection or revoke endpoint; can expires_in be shorter than 86400?

🟡 부분 · 우선순위 must · 확신 medium

Reissue immediately invalidates the prior token; one valid token per client; no refresh token [toss-openapi-json-1-2-14]. No grace period is documented. expires_in is an integer with example 86400, not a guarantee, so use the returned value [toss-openapi-json-1-2-14]. Resource 401 codes: invalid-token, expired-token, edge-blocked, login-user-not-found [toss-official-overview-mirror]. Token endpoint uses OAuth2 errors: invalid_client 401, access_denied 'IP address not allowed' 403, invalid_request/unsupported_grant_type 400 [toss-openapi-json-1-2-14]. No introspection or revoke endpoint exists [beoks-api-reference-index]. Whether a reissue-invalidated token yields invalid-token or a distinct code is unspecified. The WebSocket checks the token only at handshake [toss-asyncapi-realtime].

### T1.Q3 · Full OrderStatus enum and state machine (e.g. PENDING/OPEN/PARTIALLY_FILLED/FILLED/CANCELED/REJECTED/EXPIRED), which transitions are terminal, and whether GET /api/v1/orders/{orderId} is available for closed orders and for how long (history retention window)?

🟡 부분 · 우선순위 must · 확신 high

Enum: PENDING, PENDING_CANCEL, PENDING_REPLACE, PARTIAL_FILLED, FILLED, CANCELED, REJECTED, CANCEL_REJECTED, REPLACE_REJECTED, REPLACED; tolerate unknown codes; no EXPIRED [toss-openapi-json-1-2-14]. List groups (re-verified this run): OPEN = {PENDING, PARTIAL_FILLED, PENDING_CANCEL, PENDING_REPLACE}; CLOSED = {FILLED, CANCELED, REJECTED, REPLACED, CANCEL_REJECTED, REPLACE_REJECTED, PARTIAL_FILLED}, so a partially filled DAY order can end as PARTIAL_FILLED [toss-openapi-json-1-2-14]. CANCELED/REJECTED/REPLACED can carry partial fills. CANCEL_REJECTED/REPLACE_REJECTED are separate records; the original reverts; modify/cancel create a NEW orderId [toss-openapi-json-1-2-14][kr-broker-toss-doc]. GET /orders/{orderId} returns any state; CLOSED listing supports from/to and cursor paging up to 100 [toss-openapi-json-1-2-14]. No retention window stated; history reportedly omits app after-hours orders [be-hcm-pr-174]. WebSocket uses a separate vocabulary (PARTIAL_FILL, FILL, CANCELING, REPLACING) [toss-asyncapi-realtime].

### T1.Q4 · clientOrderId semantics: is it enforced server-side as an idempotency key within the 10-minute window (duplicate -> same orderId, 409, or new order)? What exactly happens on replay after the window? Does the server echo clientOrderId in GET /orders list and detail so ambiguous submits could be bound (ADR-0003 says binding is forbidden, but the capability matters)?

🟡 부분 · 우선순위 must · 확신 medium

clientOrderId optional, <=36 chars, [A-Za-z0-9_-]; omitted = no idempotency [toss-openapi-json-1-2-14]. Within 10 min: same key + same payload returns the earlier result (same orderId); different payload -> 422 idempotency-key-conflict; concurrent in-flight duplicate -> 409 request-in-progress [toss-openapi-json-1-2-14][toss-official-overview-mirror][be-hcm-pr-174][scjang01-tossinvest-mcp]. After 10 min the same key creates a NEW order [toss-openapi-json-1-2-14]. Replay presumably returns 200 (only success code declared; inferred). Echoed only in OrderResponse; Order list/detail does not carry it, so ambiguous submits cannot be bound server-side by clientOrderId [toss-openapi-json-1-2-14]. Unknown: replay behaviour after the original has gone terminal.

### T1.Q5 · Order cancel and modify endpoints: paths, idempotency, race semantics (cancel of partially filled order), and whether cancel-reject vs cancel-ack are distinguishable; is there cancel-all / kill-all for an account?

🟡 부분 · 우선순위 must · 확신 medium

Cancel POST /api/v1/orders/{orderId}/cancel; modify POST .../modify [beoks-api-reference-index]; both return a NEW orderId; cancel declares 200/400/401/404/409/422/429/500, no 204 [toss-openapi-json-1-2-14], though a practitioner reports 204 [scjang01-tossinvest-mcp]. Modify: KR integer quantity, US price-only, LIMIT requires price, MARKET forbids it [toss-openapi-json-1-2-14]; KR partial-fill quantity semantics (total vs remainder) ambiguous [kr-broker-toss-doc][be-hcm-pr-178]. Conflicts: 409 already-filled/canceled/modified/rejected/processing; 422 cancel-restricted/modify-restricted [toss-official-overview-mirror]. Ack vs reject is only distinguishable asynchronously: original goes PENDING_CANCEL; rejection appears as a separate CANCEL_REJECTED record, so re-read the original [toss-openapi-json-1-2-14][kr-broker-toss-doc]. No idempotency key for cancel/modify; do not resend a cancel (replay returns already-canceled) [be-hcm-pr-174]. No cancel-all/kill-all endpoint [beoks-api-reference-index]. Conditional orders use their own POST modify / DELETE cancel [beoks-current-api-notes].

## 프로젝트 함의

- ADR-0002 (docs/adr/0002-order-intent-identity.md:32) and ADR-0003 (docs/adr/0003-order-reconciliation.md:30) record 'status=CLOSED returns 400 closed-not-supported' and OPEN-only listing. Spec 1.2.14 mirror (re-verified with jq this run) contains no such string and documents CLOSED with limit/cursor/from-to; OPEN ignores limit/cursor (consistent with 'nextCursor always null'). ADR-0003's ABSENT-never-established conclusion still holds because Order does not echo clientOrderId, so fail-closed binding stays correct, but the Context facts need an amendment; ADR-0014 escalation could present a CLOSED+OPEN listing by symbol/time window as human evidence. Re-verify against live v1.2.28 since the earlier repo observation may reflect live behaviour that differs from docs.
- Rate-limit budgeting: GET /orders and /orders/{orderId} are ORDER_HISTORY (5/s shared), POST /orders and /cancel are ORDER (10/s); the 09:00-09:10 cut hits only ORDER_INFO pre-checks. configs/env.example currently has no rate knobs (only TOSS_CLIENT_ID/SECRET/BASE_URL/ACCOUNT_SEQ and TOSS_BOT_* kill-switch thresholds); any future knobs should be per group, and internal/toss backoff should honour Retry-After and X-RateLimit-Reset rather than hardcode blog figures. CLAUDE.md's 'limits: check the spec' line is consistent.
- ADR-0003 line 28 lists OrderStatus as 'PENDING, PARTIAL_FILLED, FILLED, CANCELED, REJECTED, …'. Full enum adds PENDING_CANCEL, PENDING_REPLACE, CANCEL_REJECTED, REPLACE_REJECTED, REPLACED. REPLACED is terminal only for that orderId; *_REJECTED are separate records; PARTIAL_FILLED is in the CLOSED group, so 'PARTIAL_FILLED => open' is false post-session. CANCELED/REJECTED/REPLACED may carry fills, so ADR-0006 digests must be taken at those terminals too. internal/reconciler must fail closed on unknown codes.
- ADR-0002 point 4 (deterministic clientOrderId, 10-min window) matches spec and independent practice [leejongyoung-tossinvest-cli-33]. Replay semantics are now defined: same body -> prior result; different body -> 422 idempotency-key-conflict; in-flight -> 409 request-in-progress. Both of the latter must route to the reconciler as ambiguous, never to the ADR-0012 rejection counter (TOSS_BOT_ORDER_FAILURE_THRESHOLD) as plain rejections. CLAUDE.md's no-auto-retry rule for order submission stays: after 10 minutes a replay is a new order.
- ADR-0001 confirmed (one token per client, immediate invalidation, no refresh). Amendments: use returned expires_in rather than assuming 86400; treat an unexpected invalid-token (no local reissue) as another holder reissuing and feed the token-refresh kill-switch (TOSS_BOT_TOKEN_REFRESH_THRESHOLD/WINDOW) rather than a silent re-auth loop; token-endpoint 403 access_denied/ip-not-allowed is non-retriable with its own audit reason; env.example/runbook should note the allowlisted-IP requirement.
- ADR-0006 premise confirmed: aggregate-only fills, no executionId, no fills endpoint; WS personal:order events also lack execution ids, so snapshot-delta digesting remains the design even with streaming.
- internal/market/doc.go:3 'WebSocket availability is unconfirmed' is outdated: AsyncAPI 1.2.2 defines wss://openapi-ws.tossinvest.com/ws/v1 including personal:order. Adoption needs a new ADR: the 2-connection cap lets other tools drop the bot's socket, no replay after disconnect, REST resync mandatory; use the stream only as a reconciler wake-up hint with REST GET as truth (ADR-0003).
- internal/order/doc.go treats cancel/modify as out of scope, but they exist (POST .../cancel and .../modify, NEW orderId, no idempotency key, no cancel-all). A future ADR must journal the new orderId (ADR-0002 marker pair), forbid automatic cancel resend (replay returns already-canceled and masks success), and handle CANCEL_REJECTED as a separate record. ADR-0004 halt cannot rely on a server kill-all; any flattening needs a per-order cancel loop within the ORDER budget.
- Market-hours gating: calendar publishes only a 3-business-day KST window with integrated KRX+NXT sessions; internal/market must refresh at least daily and not assume a long-range holiday list; order-hours-closed data.retryAfterAt is a fail-safe hint; US amount/fractional orders have a narrower window (open to 1 h before close).
- Contract tests: repo facts have already drifted (CLOSED listing). Pin info.version for REST (live 1.2.28) and AsyncAPI (1.2.2), fail on diffs to consumed operations/schemas, and run from the allowlisted environment because Toss hosts are unreachable from cloud sessions.

- GET /orders status=CLOSED: ADR-0002/0003 record '400 closed-not-supported'; spec 1.2.14 (re-verified) documents CLOSED with paging and lacks that string. Likely spec evolution or doc/live divergence; re-check live and amend ADRs.
- Cancel success code: scjang01-tossinvest-mcp reports 204; spec declares only 200. Handle both; spec primary.
- Rate group for order polling: earlier summaries implied ORDER_INFO; spec assigns GET /orders and /orders/{orderId} to ORDER_HISTORY.
- CLOSED group membership: one summary omits PARTIAL_FILLED; the spec includes it (re-verified).
- Event vocabulary: REST uses PARTIAL_FILLED/FILLED/PENDING_CANCEL/PENDING_REPLACE; WS uses PARTIAL_FILL/FILL/CANCELING/REPLACING. Separate enums needing explicit mapping.
- WebSocket existence: several SDKs say 'no WebSocket support' while AsyncAPI 1.2.2 and the overview define it; SDK statements describe SDK scope only.
- Daily order cap: tossinvest-mcp implements client-side daily budgets and the overview lists 422 order-limit-exceeded, but no source defines a server-side daily count; unverified.
