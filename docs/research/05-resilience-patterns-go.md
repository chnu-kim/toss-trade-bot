# Resilience patterns for a 24/7 Go process: backoff, rate limiting, single-flight, supervision, shutdown

> **왜 중요한가** — ADR-0001 single-flight token manager; internal/toss client (exponential backoff base 200ms cap 5s, 429/5xx retry on GET only, 401 one-shot reissue); internal/runtime supervisor (recover boundaries, TOSS_BOT_SHUTDOWN_TIMEOUT=10s drain), reconciler supervised ticker (ADR-0014 Decision 12). Gaps: jitter is absent in backoffDelay, client-side rate limiter for Toss limits does not exist yet, supervision restart policy for panicking loops is log-and-continue only.

수집 방식: 학술·공식/표준·업계/포스트모템·한국어 4경로 병렬 검색 → 종합·공백 판정(최대 2라운드 재수집). 출처 41건. 상태 집계: 🟡 부분 8, ✅ 답변됨 4

## 핵심 결론

- **Single-flight / request coalescing in Go (golang.org/x/sync/singleflight) and its pitfalls: context cancellation of the shared call, panics inside the shared func, stale result reuse — with respect to ADR-0001's token manager and 401 storm handling.** — x/sync/singleflight takes no context; the shared call runs under whatever ctx the leader's fn captured and errors are shared, so a cancelled leader fails all waiters [go-x-sync-singleflight, go-x-sync-singleflight-src]. A panic in fn re-panics in every Do duplicate, and for DoChan waiters is raised in a fresh goroutine, unrecoverable [go-x-sync-singleflight-src]. Forget does not cancel a hung flight; entries are dropped on completion so staleness only comes from the caller's own cache [go-x-sync-singleflight-src]. Countermeasures: run the flight on context.WithoutCancel with its own bound [go-context], recover inside fn, and let each waiter select on its own ctx. ADR-0001's custom tokenManager (internal/toss/token.go) does all three, and bounds 401 storms with compare-and-invalidate plus a 200ms holdoff. Residual risk: WithoutCancel also removes the parent deadline, so issuance is bounded only by the http.Client 10s Timeout.
- **Panic/recover boundaries in Go: what cannot be recovered (runtime fatal errors, concurrent map writes, out-of-memory, deadlock detection), goroutine leaks after recover, and guidance on 'crash-only software' vs recover-and-continue for money-moving loops.** — recover works only when called directly in a deferred function of the panicking goroutine; an unrecovered panic in any goroutine exits with code 2 [go-builtin-recover, go-runtime-docs]. Runtime throw/fatal bypass gopanic, so defers and recover never run [go-runtime-panic-src]; concurrent map access is reported via fatal("concurrent map writes"/"concurrent map read and map write") [go-runtime-maps-src], so map races kill the process whatever boundaries exist. OOM, global deadlock and stack overflow behave as throws in practice (general knowledge, not fetched). A panic re-raised by singleflight DoChan is unrecoverable [go-x-sync-singleflight-src]. Faults crash unless SetPanicOnFault (per goroutine) [go-runtime-debug]. After recover, spawned goroutines, held mutexes and half-written state remain; goleak detects leftover goroutines in tests [uber-goleak], and suture notes stuck services are leaked [suture-v4]. For money-moving paths, crash-only reasoning favours treating a panic as 'state unknown' and failing closed, reconstructing from durable/API state, over continuing [candea-fox-crash-only-hotos-2003]. Set GOTRACEBACK=all and debug.SetCrashOutput so fatal errors leave a durable record [go-runtime-debug].
- **Clock handling: monotonic vs wall clock in Go time package, NTP step/slew effects on timers and on persisted timestamps (retro: NTP wall-clock regression between ResolveIntent and FinalizeFullyAudited), leap seconds, and injecting a clock for tests.** — time.Now carries wall and monotonic readings, but comparisons use monotonic only when both operands have one; Marshal/Gob/Parse/Unix values lack it and Round/In/UTC strip it, so persisted timestamps compare by wall clock and can regress after an NTP step [go-time-monotonic]. This explains the retro's ResolveIntent vs FinalizeFullyAudited regression. Use Equal not ==, order persisted records by journal seq/rowid, and treat a wall regression as data to flag. On the host, prefer slewing over stepping (limit chrony makestep to boot, cap with maxchange; leap smear via leapsecmode slew + smoothtime) [chrony-docs-mirror, mirror only]. Inject a clock or use synctest's fake clock in tests [go-testing-synctest].
- **Deterministic simulation / time-virtualized testing of concurrent loops in Go (testing/synctest in Go 1.24+, fake clocks, race detector limitations) for supervisor and reconciler tick logic.** — testing/synctest (experimental in 1.24, Test from 1.25, Sleep from 1.27) gives each bubble a fake clock that advances only when every goroutine is durably blocked, making tickers, backoff and restart delays instant and deterministic [go-testing-synctest]. Limits: mutexes, network I/O (including httptest loopback) and syscalls (real SQLite) are not durably blocking, so use net.Pipe or in-memory fakes; bubbled timers panic outside the bubble; all-blocked with no timer reports deadlock [go-testing-synctest]. The race detector only finds races that occur in a run (general knowledge, not sourced), so combine -race with synctest-driven interleavings.

## 질문별 답변

### T5.Q1 · Exponential backoff with jitter: canonical analysis (AWS Architecture Blog 'Exponential Backoff and Jitter', Google SRE 'Handling Overload'), full vs equal vs decorrelated jitter, and when retries must be budgeted (retry budgets, adaptive throttling) to avoid retry storms against a single broker API.

🟡 부분 · 우선순위 must · 확신 medium

Capped exponential backoff without randomness keeps contending clients correlated, so retries arrive in waves. Jitter cuts total calls by more than half in the 100-client simulation; Full and Decorrelated Jitter perform about the same (Full does slightly less work), Equal is weakest [brooker-aws-backoff-jitter-2015]; the simulator is public [aws-arch-backoff-simulator]. Standard formulas (not verified on the page): Full = rand(0, min(cap, base*2^n)); Equal = d/2 + rand(0, d/2); Decorrelated = min(cap, rand(base, prev*3)). Jitter alone does not prevent retry storms: retries need a per-request cap and an aggregate budget [brooker-backoff-2022, sre-cascading-failures]. The SRE book's client-side adaptive throttling rejects locally with probability max(0,(requests-K*accepts)/(requests+1)) over a ~2-minute window, K≈2 [sre-handling-overload], corroborated by a production port [apache-beam-adaptive-throttler]. The 3-attempt per-request cap and ~10% per-client retry budget come only from secondary summaries of [sre-cascading-failures]. For a single broker API: Full Jitter on GET retries, a per-call cap (internal/toss already has maxRetries=4), and a process-wide retry budget or adaptive throttle so a broker outage does not multiply load.

### T5.Q2 · Client-side rate limiting to stay under broker limits: token bucket vs leaky bucket (golang.org/x/time/rate), per-endpoint buckets, handling Retry-After, prioritizing reconciler/kill-switch reads over strategy reads under quota pressure.

🟡 부분 · 우선순위 must · 확신 medium

golang.org/x/time/rate is a token bucket (capacity b, starts full, refill r/s), not a queueing leaky bucket; Allow drops, Reserve+Delay/Cancel schedules, Wait blocks with ctx and fails fast if the expected wait exceeds the ctx deadline [go-x-time-rate]. Per-endpoint (or per-API-group) buckets are separate Limiters. No priority exists in the package, so reconciler/kill-switch reads need protection by construction (inferred): strategy calls take a token from a strategy sub-limiter and the global limiter, safety reads only from the global one, or strategy reservations that would eat reserved headroom are cancelled. Retry-After is HTTP-date or delay-seconds [rfc9110-retry-after]; honour it as a floor on the next attempt and/or temporarily via SetLimit, noting earlier reservations can briefly overshoot [go-x-time-rate]. Adaptive throttling is a complementary self-limit when the server starts rejecting [sre-handling-overload]. Toss's actual limits are unverified: an unofficial guide reports per-group limits (ORDER_INFO 6 req/s dropping to 3 req/s 09:00-09:10) [algolab-toss-errors]; the official openapi.json must be checked before encoding numbers.

### T5.Q4 · Supervision-tree semantics (Erlang/OTP restart strategies, intensity/period limits) ported to Go (suture, oklog/run, errgroup) — when to restart a loop vs escalate to halt vs exit the process for systemd to restart.

🟡 부분 · 우선순위 should · 확신 medium

OTP: if restarts exceed intensity within period, the supervisor terminates its children and itself and escalates; default 1 in 5s, period of 5-10 minutes suggested for systems without fast human response, and do not copy settings across levels because counts multiply [erlang-otp-supervisor-principles]. suture v4 ports this as a decaying counter (threshold 5, decay 30s, jittered 15s backoff), panic counts as failure, explicit escalation errors [suture-v4]. errgroup and oklog/run are fail-together with no restart and fit exit-and-let-systemd-restart [x-sync-errgroup, oklog-run]; systemd's StartLimitIntervalSec/StartLimitBurst is the process-level intensity limit for that path [systemd-unit-startlimit]. Crash-only design makes restart the trusted recovery path [candea-fox-crash-only-hotos-2003]. Synthesized policy for this bot: restart a loop with jittered backoff within an intensity budget; for safety-critical loops (reconciler ticker) exceeding the budget escalates to BootHalt/Trip(ScopeGlobal) per ADR-0014 Decision 12 rather than exiting; exit the process only on fatal runtime errors, a failed audit sink or broken invariants, relying on ADR-0007 halted boot afterwards.

### T5.Q6 · Graceful shutdown ordering with context cancellation: draining in-flight POSTs (never cancel a POST mid-flight — treat as ambiguous), ordering of supervised loops, signal handling (SIGTERM/SIGINT/SIGHUP), and systemd TimeoutStopSec interplay with TOSS_BOT_SHUTDOWN_TIMEOUT.

🟡 부분 · 우선순위 must · 확신 medium

NotifyContext converts listed signals to cancellation with Cause naming the signal; unlisted ones keep defaults, so SIGHUP exits [go-os-signal]; cmd/bot/main.go registers only SIGINT and SIGTERM. In-flight POSTs must run on a detached (WithoutCancel) context with their own bounded timeout [go-context]; a POST that times out is ambiguous (ADR-0003). Order: stop strategy, drain submits and their persistence, optional final reconcile (or leave to boot scan), fsync audit, write the clean-shutdown sentinel; oklog/run does not order interrupts, so sequencing must be explicit [oklog-run]. Send STOPPING=1 at shutdown start [coreos-go-systemd-daemon]. systemd sends KillSignal (SIGTERM) then SIGKILL/FinalKillSignal after TimeoutStopSec [systemd-kill, systemd-service]; KillMode=mixed or control-group is appropriate. Constraint chain: POST timeout + durable persist timeout <= TOSS_BOT_SHUTDOWN_TIMEOUT < TimeoutStopSec. The repo's 10s default is not above the 10s HTTP timeout plus the 30s durablePersistTimeout. systemd's default TimeoutStopSec (commonly 90s) was not verified.

### T5.Q7 · HTTP client hardening in Go: net/http timeouts (dial, TLS, response header, idle), connection reuse, body size limits, HTTP/2 behaviour, DNS re-resolution for long-lived processes, and proxy/CA handling.

🟡 부분 · 우선순위 should · 확신 medium

Client.Timeout covers dial, redirects and body read and keeps running after Do returns [go-net-http]; phases can be bounded with Dialer.Timeout, TLSHandshakeTimeout, ResponseHeaderTimeout, IdleConnTimeout [valsorda-cloudflare-go-http-timeouts-2016]; Dialer.Timeout has no default and KeepAlive defaults to 15s [go-net-dialer-resolver]. Reuse requires draining and closing bodies; DefaultMaxIdleConnsPerHost is 2, so a single-host client should raise it; a custom Transport needs ForceAttemptHTTP2 for HTTP/2; proxies come from HTTP(S)_PROXY/NO_PROXY [go-net-http]. Client-side response limits use io.LimitReader (internal/toss caps at 1 MiB). DNS caching is undocumented [go-net-dialer-resolver]; inferred behaviour is re-resolution on each new dial, so IdleConnTimeout bounds how long a stale IP persists. httptrace exposes the lifecycle for diagnostics [go-net-http-httptrace]. Custom RootCAs handling was not sourced.

### T5.Q8 · Timeout vs ambiguous-write semantics: how to pick POST timeout so that 'client timed out but server executed' is minimized; relationship to settle window and server-side processing time.

🟡 부분 · 우선순위 should · 확신 low

No source quantifies the 'client timed out but server executed' window. httptrace's WroteRequest/GotFirstResponseByte let the client classify failures before the request was written (dial, TLS, header write) as definitely not sent, and failures after as ambiguous [go-net-http-httptrace, go-net-http]. Vendors with idempotency keys resolve ambiguity by retrying with the same key [stripe-idempotent-requests]; Toss lacks this per the ADRs, so ambiguity is resolved by state re-query (ADR-0002/0003), never resubmission. Synthesized practice: short dial/TLS timeouts, a ResponseHeaderTimeout well above the broker's p99 processing time, phase-based error classification, and ADR-0014's settle window at least POST timeout plus propagation delay. Toss latency figures were not retrieved.

### T5.Q9 · Clock handling: monotonic vs wall clock in Go time package, NTP step/slew effects on timers and on persisted timestamps (retro: NTP wall-clock regression between ResolveIntent and FinalizeFullyAudited), leap seconds, and injecting a clock for tests.

### T5.Q10 · Memory and resource stability over weeks: goroutine/FD leak detection (goleak, pprof), GC tuning (GOMEMLIMIT), log rotation, and long-run soak testing practices for daemons.

🟡 부분 · 우선순위 should · 확신 medium

GOMEMLIMIT is a soft limit on runtime-managed memory, applies even with GOGC=off; set somewhat below the cgroup MemoryMax, since too low causes near-continuous GC [go-runtime-debug, golang-soft-memory-limit-proposal-48409]. GOMAXPROCS follows the cgroup CPU quota [go-runtime-docs]. Use goleak in tests [uber-goleak], and pprof delta profiles (goroutine/heap with seconds=N) on a localhost-only listener for production leak hunting [go-net-http-pprof, go-diagnostics]. Bound the SQLite pool [modernc-sqlite]. FD-leak monitoring, log rotation (journald vs logrotate) and soak-test methodology were not sourced.

### T5.Q11 · Health signalling for a non-HTTP daemon: systemd sd_notify watchdog, healthcheck files, exposing a minimal /healthz, and ensuring health reflects 'able to reconcile' not just 'process alive'.

🟡 부분 · 우선순위 should · 확신 medium

systemd watchdog: WatchdogSec= enables supervision, the daemon reads WATCHDOG_USEC/WATCHDOG_PID and sends WATCHDOG=1 at about half the interval; if pings stop, systemd kills (and with Restart= restarts) the service [sd-watchdog-enabled, systemd-service, coreos-go-systemd-daemon]. go-systemd is a no-op without NOTIFY_SOCKET [coreos-go-systemd-daemon]. Synthesized: gate WATCHDOG=1 on 'reconciler ticker completed a tick within N x interval and a valid token is held', and when the predicate fails trip a global halt first, then stop pinging, so a restart lands in ADR-0007's halted boot. The same predicate can back a file-mtime check or loopback /healthz. No published example of progress-based watchdog gating was found.

## 프로젝트 함의

- ADR-0001 is confirmed and exceeds stock singleflight: token.go runs the flight on WithoutCancel, recovers panics and lets waiters abandon on their own ctx [go-x-sync-singleflight-src]. WithoutCancel strips the deadline, so issuance is bounded only by http.Client Timeout 10s; add a test that the flight stays time-bounded when the issuer ignores ctx.
- internal/toss backoffDelay (client.go:502; base 200ms, cap 5s) has no jitter [brooker-aws-backoff-jitter-2015]. Recommend Full Jitter via an injectable rand seam; risk:high under ADR-0001/0003; the no-retry rule for POST is unchanged.
- maxRetries=4 (client.go:40) bounds retries per call, not in aggregate. Add a process-wide retry budget or SRE-style adaptive throttle before strategy loops exist [sre-handling-overload, sre-cascading-failures].
- No ADR covers a client-side rate limiter. Confirm Toss limits in openapi.json first (the only numbers found are unofficial [algolab-toss-errors]), then /architect an ADR: x/time/rate per API group, Retry-After honoured as a floor [rfc9110-retry-after], and reserved capacity so ADR-0003/0014 reconciler and ADR-0004 kill-switch reads cannot be starved by strategy reads [go-x-time-rate].
- Repo-internal conflict: internal/runtime/supervisor.go states it 'does NOT restart the goroutine and does NOT escalate', while ADR-0014 Decision 12 requires the ticker/reconciler goroutine to be supervisor-restarted and promoted to killswitch.BootHalt()/Trip(ScopeGlobal) when it cannot be kept alive. Verify the #36 main wiring implements this; if not, it is an ADR-0014 conformance gap. Model the fix on OTP intensity/period (period in minutes) or suture's decaying counter with jittered backoff [erlang-otp-supervisor-principles, suture-v4].
- Fatal runtime errors (concurrent map writes, throws) bypass every recover boundary [go-runtime-panic-src, go-runtime-maps-src], so CLAUDE.md 'never die' cannot be absolute. Rely on ADR-0007's halted boot after unclean exit, keep go test -race as CI gate, and set GOTRACEBACK=all plus debug.SetCrashOutput to a file beside the audit log [go-runtime-debug]. If deployed under systemd, set StartLimitBurst so a crash loop stops rather than flapping [systemd-unit-startlimit].
- Shutdown timing: DefaultShutdownTimeout = 10s (config.go:53) equals the HTTP Client.Timeout and is shorter than submit.go's durablePersistTimeout (30s). A POST or ack persistence started just before SIGTERM can outlive the drain; ADR-0003 keeps it fail-closed (ambiguous) but the default should be >= POST timeout + durablePersistTimeout, with systemd TimeoutStopSec larger still [systemd-kill, systemd-service].
- cmd/bot/main.go registers only SIGINT/SIGTERM; SIGHUP keeps its default and exits without the sentinel [go-os-signal], leading to an ADR-0007 halted boot. Safe but surprising: register SIGHUP or document it in a runbook.
- ADR-0003's ambiguous classification could use httptrace WroteRequest: failures before the write are definitely not sent, reducing false-ambiguous counts toward ADR-0014's backlog threshold [go-net-http-httptrace]. Stripe-style idempotency keys [stripe-idempotent-requests] are the reference design ADR-0002's intent identity substitutes for.
- The NTP retro is explained by time.Time losing its monotonic reading when persisted [go-time-monotonic]; store/audit invariants should order by journal seq/rowid, not wall-clock comparison. Runbook: configure chrony to slew rather than step after boot [chrony-docs-mirror].
- Health: no sd_notify exists. If added, gate WATCHDOG=1 on the ADR-0014 ticker's last successful tick and trip halt before stopping pings [sd-watchdog-enabled, coreos-go-systemd-daemon].
- Tests: supervisor and ticker logic can use synctest (toolchain >= 1.25) with in-memory fakes instead of SQLite/httptest; add goleak.VerifyNone to Supervisor and App shutdown tests [go-testing-synctest, uber-goleak].

## 출처 간 상충

- Jitter variant ranking: most pools report Full ≈ Decorrelated with Equal weakest; one round-2 pool says Full and Equal make about the same number of calls and Decorrelated makes more. Both are excerpt-level; resolve by reading the AWS post or running aws-arch-backoff-simulator. Undisputed: any jitter beats none.
- Fail-together exit (errgroup, oklog/run) versus restart within an intensity budget (OTP, suture): different policies; ADR-0014 Decision 12 chooses restart with escalation to global halt for the reconciler, while systemd StartLimit* governs the exit path.
- Crash-only (stop = crash) versus CLAUDE.md 'never die': recover-and-continue suits loops that re-derive state each iteration; money-moving paths should fail closed on panic; fatal runtime errors make 'never die' impossible to guarantee [go-runtime-panic-src].
- Repo-internal: supervisor.go 'no restart, no escalation' vs ADR-0014 Decision 12 'supervisor restarts the ticker and escalates'. Resolve in wiring or by ADR amendment.
- SRE retry-budget figures (3 attempts, 10%) appear only in secondary summaries; the adaptive-throttling formula is corroborated by Apache Beam's implementation. Chapter numbering confusion (21 vs 22) resolves as ch.21 Handling Overload, ch.22 Addressing Cascading Failures.
- synctest status: the 2024 proposal-era notes (experimental, GOEXPERIMENT in 1.24) are superseded by pkg.go.dev (Test in 1.25, Sleep in 1.27).
- brooker.co.za/blog/2022/08/11/backoff.html title differs between pools ('Fixing retries with token buckets and circuit breakers' vs 'What is Backoff For?'); neither fetched the page.

### 출처 요약

- **`go-x-sync-singleflight-src`** — The implementation shows panic and Goexit behaviour that the API page leaves out. A panic in fn is wrapped with its stack and re-panicked in every Do caller. For DoChan waiters it is re-panicked in a new goroutine, so it cannot be recovered and the process crashes. The shared call runs under whatever context the first caller's fn captured. The map entry is removed on completion, so no result is cached afterwards. _(접근: open access; fetched)_
- **`go-x-sync-singleflight`** — API contract for Do, DoChan, Forget and the shared flag. It takes no context.Context, so cancelling the shared call is the job of the fn. Errors are shared: every duplicate caller receives the same error. _(접근: open access)_
- **`go-x-time-rate`** — Token-bucket Limiter: starts full, holds at most b tokens, refills at r per second. Allow drops, Reserve returns a delay (cancellable), Wait blocks and respects ctx, failing early if the expected wait exceeds the ctx deadline. SetLimit adjusts the rate at runtime. No priority classes. _(접근: open access; fetched)_
- **`brooker-aws-backoff-jitter-2015`** — Canonical simulation (optimistic concurrency control, contending clients) comparing capped exponential backoff with Full, Equal and Decorrelated Jitter. Backoff without jitter leaves clients correlated; jitter sharply cuts total calls. Seen via search excerpts only across several pools; formulas not verified on the page. _(접근: open access; search excerpts only (aws.amazon.com unreachable))_
- **`aws-arch-backoff-simulator`** — Apache-2.0 simulator behind the jitter post's graphs; can reproduce jitter comparisons with the bot's parameters (base 200ms, cap 5s). Only the landing page was fetched. _(접근: open access; landing page fetched)_
- **`sre-handling-overload`** — Client-side adaptive throttling: each client tracks requests and accepts over a trailing window (about two minutes) and rejects locally with probability max(0,(requests-K*accepts)/(requests+1)); K=2 is the example, lower K is more aggressive. Also separates retry budgets, per-request retry caps and request criticality. Content from search excerpts in multiple pools plus a derived implementation (Apache Beam); page not fetched. _(접근: open access; fetch blocked (DNS), excerpt-level)_
- **`sre-cascading-failures`** — Canonical treatment of retry amplification: randomized exponential backoff, per-request retry limits and per-client retry budgets, and the multiplication of retries across layers.
